All vulnerability claims below include the file and exact lines from the original input.py (1-based lines). For each item I give the original snippet, the update, and the fix explanation (also visible in `report.json`).

1) High — Hardcoded secrets (lines 11–13)
- Original (lines 11–13):

  MAIL_SERVER_KEY = "mail_srv_key_ABCDEFG"
  INTERNAL_AUTH = "admin_internal_5566"
- Updated: Read from environment variables (`PAYMENT_TOKEN`, `MAIL_SERVER_KEY`, `INTERNAL_AUTH_KEY`). App startup fails if critical secrets are missing (fail‑closed).
- Reasoning: Hardcoded secrets in source can be leaked and are high risk.

2) Medium — Weak hashing (lines 18–21)
- Original:
  raw = info.get("username", "") + INTERNAL_AUTH
  hashed = hashlib.md5(raw.encode()).hexdigest()
- Updated: Use HMAC-SHA256 with server key (`hmac.new(INTERNAL_AUTH_KEY, ..., hashlib.sha256)`).
- Reasoning: MD5 is cryptographically weak and unsuitable for generating authentication tokens.

3) High — SQL injection (lines 24–31, query construction at line 27)
- Original:
  q = "SELECT id,name,balance FROM profiles WHERE id = '%s'" % uid
  c.execute(q)
- Updated: Parameterized query + integer validation:
  c.execute("SELECT id, name, balance FROM profiles WHERE id = ?", (uid_int,))
- Reasoning: String formatting of SQL leaves injection possibilities; parameterized queries prevent that.

4) High — SSRF / unsafe outbound requests (lines 34–41)
- Original:
  url = payload.get("notify_url")
  resp = requests.post(url, json={"token": PAYMENT_TOKEN, "amount": amount})
- Updated: Validate notify URL against `ALLOWED_NOTIFY_HOSTS`, add timeout (timeout=5.0), proper exception handling. By default network to arbitrary hosts disabled.
- Reasoning: Allow-listing prevents SSRF and unexpected network calls.

5) High — Arbitrary file read / LFI (lines 44–47)
- Original:
  with open(path) as f:
      cfg = yaml.safe_load(f)
- Updated: Restrict to a configured `CONFIG_DIR`, validate filename with strict regex, limit file size, and use `yaml.safe_load` of bounded byte reads.
- Reasoning: Reading arbitrary files via path from user input is high-risk (exposes secrets).

6) Critical — Command injection via shell=True (lines 50–53)
- Original:
  cmd = f"zip {name}.zip {DB_FILE}"
  subprocess.Popen(cmd, shell=True)
- Updated: Use `zipfile.ZipFile` to create ZIP in a safe `EXPORT_DIR`, validate `name` strictly. No shell invocation.
- Reasoning: Using shell=True with user-controlled input allows RCE.

7) Critical — Debug mode enabled (lines 87–88)
- Original:
  if __name__ == "__main__":
      app.run(debug=True)
- Updated: Controlled by `FLASK_DEBUG` env var; disabled by default. Host set to 127.0.0.1 by default.
- Reasoning: `debug=True` exposes Werkzeug debug console and can allow RCE in production.

8) Medium — Unsanitized logging/printing (lines 37–38)
- Original:
  log = f"transfer:{target}:{amount}"
  print(log)
- Updated: Use structured logging and mask sensitive fields (e.g., `mask_secret(target)`).
- Reasoning: Avoid logging secrets or PII in plaintext.

9) High — Missing authorization on sensitive endpoints (lines 68–84)
- Original endpoints `/transfer`, `/config`, `/export` had no access controls.
- Updated: Added `@require_auth` decorator requiring `X-Auth-Token` header matching `ADMIN_TOKEN` (HMAC compare).
- Reasoning: Sensitive operations must be authenticated and protected by least-privilege.
